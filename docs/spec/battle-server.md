# SPEC: 対戦サーバ

人間同士のオンライン対戦を成立させ、その対局を AI の学習に使える形で残すための層である。
エンジン（`engine/`、git submodule として取り込んだ `poke-tcg-engine`）の
`docs/spec/engine-core.md`（以下コア SPEC）がスコープ外へ置いた 4 つ、すなわち
対戦サーバのプロトコル、デッキ構築バリデーション、イベント射影の詳細規則（コア §9.2）、
リプレイの永続形式を、この文書が引き取る。

ルールの判定は 1 行もここに書かない。ルールはコアが持つ。

## 0. スコープ

### 対象

- 対戦の進行の権威（サーバが `GameState` を持ち、両者の入力を受けて `applyMove` を呼ぶ）。
- 座席ごとの情報の秘匿。
- 対戦中の観戦。
- 通信のプロトコルと、切断と再接続と持ち時間。
- デッキの提出と検証。
- 対局ログの形式と保存と再生。
- 相手を見つける手立て。

### スコープ外

- 描画（クライアントの見た目）。プロトコルが運ぶ値の形までをこの文書が定め、その先は持たない。
- レーティングとアカウント。§7 に導線だけ置く。
- 学習そのもの。ログの形式までがこの文書で、そこから先は `docs/design/ai-training-loop-skeleton.md`。

---

## 1. 不変条件

コアの C-1 から C-5 を前提に、サーバ側で追加して守る性質である。

- **S-1 権威はサーバが持つ `GameState` にある。** クライアントは盤面もダメージもサイドの枚数も申告しない（コア C-5 の運用側）。クライアントから来る値は「どの手を選んだか」だけである。
- **S-2 クライアントへ出る値は、必ず射影を通る。** `ApplyResult.state` と `ApplyResult.events` をそのまま配信する経路を作らない。座席へ出てよいのは `playerView(state, seat)` と `projectEvents(events, seat)` の戻り値、および**手番側だけへ送る合法手**である。観戦者へ出てよいのは `spectatorView(state)` と `projectEvents(events, "spectator")` の戻り値だけである（3.6 節）。この規律はコア §9.1 が明示的にサーバ側の責務としたものである。
- **S-3 seed は対戦が終わるまで公開しない。** seed はシャッフルを完全に決めるので、対戦中に渡すと相手の山札とサイドがすべて割れる。
- **S-4 対局ログは seed と move 列で足りる。** 局面もイベントも保存しない。コア C-4（同一 seed ＋同一 move 列 → 同一の状態列とイベント列）がこれを保証する。
- **S-5 エンジンへ時刻と通信を持ち込まない。** 持ち時間、切断、投了はすべてサーバの語彙であり、`Move` にも `GameState` にも `WinReason` にも足さない（コア D-3）。
- **S-6 対局ログは、それを作ったエンジンの指紋を記録する。** エンジンを直すと同じ move 列が別の対戦を再生しうる。エンジンの指紋が無いログは、再生できるかどうかを言えない。

## 2. 対戦の進行

### 2.1 いつでも手を持つのは 1 人である 【決定】

`legalMoves` は、選択待ちがあれば最上段の `Choice` の owner の手だけを、無ければ `state.turnPlayer`
の手だけを返す（コア SPEC §4、§6.4）。**両者が同時に手を持つ状態は存在しない。**
対戦準備の場出しも、きぜつ後の昇格も、相手の番の割り込みも、すべて `Choice` を介して
「そのとき手を持つ 1 人」へ集約される。

したがってサーバは、その時点の手番側を state から導く。座席と手番の対応をサーバ側で別に持たない。

```
手番側 = state.choices.at(-1)?.owner ?? state.turnPlayer   （phase === "gameover" なら不在）
```

### 2.2 手の受理 【決定】

サーバは 1 つの `Move` を受け取るたび、次の順に検査する。順序を入れ替えない。

1. 送信元の座席が手番側であること。違えば `not-your-turn` を返し、state は変えない。
2. 送信された `stateVersion` が現在値と一致すること。違えば `stale-version` を返し、現在の局面一式を送り直す。
3. `legalMoves(state)` に `movesEqual` で一致する手があること。無ければ `illegal-move` を返す。

`stateVersion` は 1 手の適用ごとに 1 増えるサーバ側の整数である。`state.eventSeq` を流用しない
（イベント数は手ごとに飛ぶので、クライアントが次の値を予測できない）。
この検査は二重送信と、古い画面から押された手を、同じ 1 つの仕組みで弾く。

**検査 3 の失敗は対戦を終わらせない。** コア §2.1 は `applyMove` が非合法手に例外を投げると定め、
その例外をエラー応答へ変換する責務を呼び出し側（このサーバ）に置いた。
サーバは `legalMoves` との照合で先に弾き、`IllegalMoveError` が実際に飛んできた場合は
サーバ側の欠陥として記録する（クライアントの責任にしない）。

### 2.3 投了と時間切れは move ではない 【決定】

`Move` に投了を足さない。根拠は 2 つある。

- 投了はルール上の敗北条件ではなく対戦の運用である。`WinReason` の 4 値（`prizes-taken`、`no-pokemon`、`deck-out`、`effect-declared`）はいずれも盤面から導かれる。
- 行動空間に投了を足すと、学習する方策がそれを選べるようになる。**投了を選べる方策は、学習の初期に投了へ収束しうる。** 対戦の都合で行動空間を広げない。

投了と時間切れは、engine の `outcome` とは別の `matchResult` としてサーバが持つ。
ログは両方を持つ（§6.2）。局面としての勝敗が付かないまま終わった対戦では `outcome` が `null` になる。

## 3. プロトコル

### 3.1 通信方式は WebSocket 1 本とする 【決定】

座席ごとに 1 本の WebSocket を張り、その上で JSON のメッセージを双方向に流す。

根拠。この対戦は手番制だが、**片側の入力が他方への出力になる**ので、サーバからの push が要る。
相手の手、持ち時間の進み、相手の切断はいずれもクライアントが問い合わせる性質のものではない。
HTTP のポーリングは遅延と無駄な往復を持ち込み、SSE ＋ POST は接続を 2 本に分けたぶん
座席の生死の判定が 2 箇所に散る。WebSocket なら「接続が生きているか」と「座席が繋がっているか」が一致する。

実装は Cloudflare Workers の WebSocket をそのまま使い、socket.io は採らない。独自のフレーミングと
再接続層を持ち込むと、この文書が定めるプロトコルの上にもう 1 段の意味論が乗る。

**対戦サーバは Durable Object 1 つに置く。** 【決定】
生きている対戦もマッチングの列もその 1 つのメモリにあり、同じ部屋の 2 人が別の場所に着くと出会えない。
Worker が受けるのは `/api/` と `/ws` だけで、どちらもこの 1 つへ回す。画面（`public/`）は
静的アセットとして配り、Worker を通さない。

**ハイバネーションは使わない。** 持ち時間の時計はメモリで回っていて、眠るとそれが止まる。
定期処理（持ち時間とスイープ、5 秒ごと）は、対戦か開いた接続がある間だけ回す。タイマーが残っていると、
誰もいなくても Durable Object の稼働時間に数えられる。
1 つ（128 MB）を 1 日中動かしても 128 MB × 86,400 秒 = 11,059 GB-s で、無料枠の 1 日 13,000 GB-s に収まる。

**対戦が残っている間は、1 分ごとにアラームを置く。** 要求もイベントも無いまま 70〜140 秒経つと、
Durable Object はメモリから降ろされ、生きている対戦ごと消える。両方の座席の回線が切れただけで
対戦が消えないように、アラームを鳴らして降ろさせない。中で回すタイマーは、降ろさない理由に数えられない。

**マッチング（7 節）は HTTP に載せる。** 【決定】
相手を探す往復は要求と応答で足り、サーバからのプッシュが要るのは対戦が始まってからである。
マッチングまで WebSocket に載せると、対戦のプロトコルに対戦でないメッセージが混ざる。

**HTTP のエラー応答は 3 つの形しか持たない。** 【決定】

| 形                          | いつ                             | 中身                                          |
| --------------------------- | -------------------------------- | --------------------------------------------- |
| `400 { error }`             | 要求そのものの形が違う           | 送り手の誤りなので 1 文で足りる               |
| `400 { ok: false, errors }` | 形は通るが、デッキが規則に反する | 読む人が直せるので、反した条件を並べる        |
| `4xx { code, error }`       | 画面の側が分岐するエラー応答     | `error` は人が読む文、`code` は機械が読む合図 |

**例外の `message` を外へ出さない。** 出していたときは、エンドポイントを 1 つ足すたびに
`Cannot read properties of null` のような内部の文言が漏れる箇所が 1 つ増えていた。
想定していない例外は 500 と決まった文で返し、中身はサーバ側のログへ置く。

**番号だけで分岐しない。** 404 は、無い道でも、前の版が動いているサーバでも、
間に挟まった中継でも返る。クライアントが取り消せない始末（保存したシークレットを捨てるなど）を
するときは、`code` の付いた応答だけを本物として扱う。

**`{ ok: false, errors }` で返す応答にも、デッキの違反でない理由なら `code` を付ける。**
`/api/join` はアカウントが無いことも同じ形で断る。`code` が無いと画面は文言でしか
見分けられず、覚えているアカウントを読み直しに行けない。

### 3.2 メッセージ 【決定】

クライアント → サーバ

| `t`       | 中身                   | 意味                             |
| --------- | ---------------------- | -------------------------------- |
| `hello`   | `seatToken`            | 座席に就く。再接続もこれ 1 つ    |
| `move`    | `stateVersion`, `move` | 手を指す（2.2 節の検査を受ける） |
| `concede` | なし                   | 投了する                         |
| `ping`    | なし                   | 生存確認。サーバは `pong` を返す |

サーバ → クライアント

| `t`       | 中身                                                                                             | 意味                                                             |
| --------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| `sync`    | `matchId`, `seat`, `stateVersion`, `view`, `legalMoves`, `clock`, `seedCommit`, `spectatorToken` | 局面一式。`hello` の直後と、`stale-version` の応答として送る     |
| `delta`   | `stateVersion`, `events`, `view`, `legalMoves`, `clock`                                          | 1 手が適用された。両座席へ送る                                   |
| `reject`  | `reason`, `stateVersion`                                                                         | 手を受理しなかった。理由は 2.2 節の 3 値                         |
| `ended`   | `matchResult`, `outcome`, `seed`, `seedNonce`, `seedShares`, `view`                              | 対戦が終わった。ここで初めて seed を明かす（S-3）                |
| `pending` | なし                                                                                             | 席は取れたが、シェアがそろわず対戦がまだ始まっていない（6.4 節） |
| `pong`    | なし                                                                                             |                                                                  |
| `error`   | `message`, `code`（3.3 節の合図のときだけ）                                                      | 受け取れなかった。接続は切らない                                 |

**形の違う 1 通は、受け手へ渡す前に断る。** 【決定】
座席に就いた相手は、対戦が終わるまで何度でも送れる。`t` を読むだけで落ちる値（`null` など）を
そのまま渡すと、配った先の処理が途中で例外を上げる。手を進めかけたところで止まれば、
その対戦の状態が半端に残る。断り方は `error` 1 通で、
接続は切らない。形が違うだけなら、次の 1 通は通ってよい。

**`move` の中身の形は、ここでは見ない。** 【決定】
`Move` はエンジンの型なので、サーバ側へ写すとエンジンが手を増やすたびに 2 か所を直すことになり、
写し忘れたぶんは「正しい手なのに断られる」形で出る。受けた手は `legalMoves` と**構造ごと**
突き合わせてから適用する（2.2 節の検査 3）ので、合法手と 1 欄でも違う object はそこで落ちる。

**座席を決めるのは接続の `seatToken` である。** 【決定】
`hello` に載ってきた値では決め直さない。決め直すと、相手の座席トークンを 1 通送るだけで
相手の座席の `view` が見える。

`legalMoves` は**手番側の座席へだけ**配列を入れ、他方へは `null` を入れる（S-2）。
`view` は `playerView` の戻り値そのもの、`events` は `projectEvents` の戻り値そのものである。
この 3 つを組み立てるのは `src/hub.ts` の `syncFor` と `deltaFor` だけとし、
ほかの経路から座席へ値を送らない。

**`delta` は毎手フルの `view` を運ぶ。差分を送らない。** 【決定】
`playerView` の JSON は実測で平均 5.1 KB、1 局 158 手（一様ランダムの自己対戦での実測値）で
両座席合わせて 1.6 MB になる。差分プロトコルはこの帯域と引き換えに、
「クライアントが持つ盤面」という第 2 の権威を作る。S-1 を機械的に守れるほうを採る。

### 3.3 再接続 【決定】

座席は `seatToken`（対戦の開始時に発行する推測不能な文字列）で同定する。
接続が切れても対戦は終わらず、同じ `seatToken` での `hello` が座席を取り戻して `sync` を受ける。
サーバは局面を持っているので、再接続に特別な復元の手順は要らない。

**繋ぎ直せるかどうかは、`seatToken` を持ち続ける側で決まる。** 参照クライアントは
これを localStorage に置き、開き直したときに同じ座席へ繋ぎに行く。サーバがその座席を
知らなければ（対戦がもう終わっていれば）、マッチングの画面へ戻す。

**参照クライアントは、切れた接続を読み込み直すのを待たずに繋ぎ直す。** 【決定】
切断中も時計は流れる（3.4 節）ので、読み込み直すまで戻れないと、気付かないうちに時間切れで負ける。
間隔は 1 秒から倍々に延ばし、30 秒を上限にする。サーバが落ちて戻ったときは全員が一斉に繋ぎ直すので、
それぞれの間隔を半分から 1 倍のあいだでばらす。間隔を 1 秒へ戻すのは、繋がってから 30 秒続いた接続が
切れたときだけにする。繋がるたびに戻すと、繋がってすぐ切れる状態が続くあいだ、1 秒おきに繋ぎに行き続ける。
繋ぎ直しているあいだは、そう画面に出し、手と投了を押せなくする。
観戦の接続も同じように繋ぎ直す。ただし断られたとき（`error` が届いてから閉じたとき）と、
開いてから一度も繋がらなかったときは、そこでやめる。

**座席を知らないことは、`error` の `code: "seat-not-found"` で伝える。** 【決定】
クライアントが `seatToken` を捨てるのは、この合図を受けたときだけとする。何も届かないまま
閉じた接続からは判断しない。回線が一瞬切れたときも、Upgrade を通さない中継を挟んだときも、
サーバが接続の受け付けで落ちたとき（1011 で閉じる）も同じ形で閉じるので、そこで捨てると
まだ続いている対戦へ戻れず、座らないまま時間切れで負ける。3.1 節の「番号だけで分岐しない」と
同じ考え方である。開いてから一度もサーバが座席を知っている印（`sync` か `pending`）を返さないまま
閉じたときは、繋ぎ直さずに、座席を覚えたままマッチングの画面を出す。盤面の画面に留めると、
繋がらない状態が続いたときに対戦を始める画面へ出られない。

シェアを出した座席は、席に着く接続に `seedShare` も付ける（6.4 節）。両座席がシェアを開くまで
対戦は始まらないので、それまでの接続には `pending` だけが届く。`pending` も、サーバがその座席を
知っている印である。これを待たずに「`sync` の前に切れたら席を失った」と読むと、始まる直前の
対戦から降り、座らないまま時間切れで負ける。

同じ `seatToken` で 2 本目が繋がったら、古いほうを閉じる。閉じる前に、古いほうへ
`error` の `code: "seat-replaced"` を送る。【決定】 クライアントはこれを受けたら繋ぎ直さない。
繋ぎ直すと今度は新しいほうが閉じられ、同じ座席を開いた 2 つのタブが互いを追い出し続ける。
同じ理由で、参照クライアントのタブどうしは座席に繋がったことを `BroadcastChannel` で知らせ合い、
知らせを受けたタブは繋ぎ直しをやめる。繋ぎ直しを待っていたタブがあとから繋ぐと、
そのあいだに開いて指しているタブのほうが閉じられる。
観戦は `seatToken` ではなく `spectatorToken` で繋ぐ別の経路である（3.6 節）。

### 3.4 持ち時間 【決定】

座席ごとに「1 手の制限 60 秒」と「持ち時間のバンク 15 分」を持つ。
手番側の 60 秒を越えたぶんがバンクから減り、バンクが尽きた時点でその座席の時間切れ負けとする。

**時間切れで自動の手を指さない。** 【決定】
自動の手は、その人が選んでいない手をその人の座席の名前でログへ混ぜる。
学習の側から見ると、区別できる印を付けたうえで捨てるしかない行が増えるだけである。
時間切れ負けは単純で、ログも汚さない。

**切断そのものには罰を置かない。** 【決定】
切断中も時計は流れる。回線が不安定なだけの人を切断即負けで罰しないこと、
切断を使った引き延ばしが時計に吸収されることが、同じ 1 つの規則から出る。
「切断の猶予時間」という概念を別に作らない。

### 3.5 接続に掛ける制限 【決定】

**1 通の上限は、HTTP の本文と同じ 64 KB とする。**
座席に就いた相手は、対戦が終わるまでいくらでもこちらへ送れる。運ぶのは 1 手と `offered` だけなので
この上限に収まり、超えた 1 通は、その接続だけを閉じる（close code 1009）。大きさは UTF-8 のバイト数で数える。

**画面が 20 秒ごとに `{ t: "ping" }` を送り、サーバは 150 秒何も届かない接続を切る。** 【決定】
線が途中で切れると、どちらの側も切れたことに気付かないまま接続が残る。閉じたことが
伝わらないので `close` も出ない。3.3 節の再接続は**新しい接続が来たとき**の話なので、
来ないまま残った接続はここでしか見つからない。
Cloudflare Workers にはサーバから WebSocket の ping を送る手段が無いので、生きていることは画面の側から伝える。
サーバは `pong` を返す（3.2 節）。観戦者も同じものを送る。
切っても対戦は終わらない（3.4 節）。サーバは局面を持っているので、同じ `seatToken` で
繋ぎ直せば座席に戻る（3.3 節）。

**待つ長さを短くしない。** Chrome は 5 分より長く隠れたタブのタイマーを 1 分に 1 回へ間引くので、
別のタブで相手の手番を待っている人の `ping` は 1 分おきになる。詰まっているだけで、待てば戻る接続も切ることになる。
切られた側は繋ぎ直せる（3.3 節）が、そのあいだも時計は流れる（3.4 節）。

**画面の側は、`ping` に答えない接続を切れたものとして繋ぎ直す。** 【決定】
線が途中で切れたときに `close` が来ないのは画面の側も同じで、待っていると繋ぎ直しが始まらない。
開いてから、または `ping` を送ってから、次に `ping` を送るときまでに何も届かなければ切れたと見なす。
サーバは繋いだ接続へすぐ何か 1 通を返し、`ping` には `pong` を返すので、生きている接続なら必ず何か届く。
黙っていた長さでは決めない。隠れたタブではタイマーが間引かれ、眠っているあいだは止まるので、
戻った直後に、答えている接続まで切ることになる。

**1 通の処理の誤りで、指している全員を巻き添えにしない。** 【決定】
1 通を処理して投げた例外は、その 1 通の分だけで受け止めてログへ置く。閉じた接続へ送るのは普通のことなので、
そこでも投げさせない。

### 3.6 観戦 【決定】

**観戦者に見えるのは、どちらの座席も相手について見えているものだけである。**
`spectatorView(state)` は両座席を、コア SPEC §9.1 の表の「相手から」の列で持つ（コア §9.4）。
手札は両者とも枚数だけ、山札とウラのサイドも枚数だけ、`Choice` の中身はどちらのものも出ない。
イベントは `projectEvents(events, "spectator")` で、どちらの当事者でもない宛先として伏せる。

したがって、観戦者が座席の片方に情報を流しても、その座席が知らないことは何も伝わらない。
観戦を遅らせて配る必要も、観戦者を座席の関係者かどうかで分ける必要も、ここから出てこない。

**観戦トークン（`spectatorToken`）は対戦ごとに 1 つ作り、両座席へ渡す。** 【決定】
`sync` に載せるので、繋ぎ直した座席も受け取れる。誰に渡すかは座席の側が決める。
どちらが渡しても相手に不利は生じない（前段）ので、座席ごとに分けない。

**生きている対戦の一覧は出さない。** 【決定】
観戦できるのは観戦トークンを渡された人だけである。済んだ対戦を読めるのが指した本人だけなのと同じく（6.6 節）、
誰がいつ指しているかを誰にでも見せる理由が無い。一覧が要るようになったら、
座席が「公開してよい」と選んだ対戦だけを載せる形にする。

**繋ぎ方は座席と同じ `/ws` で、`spectatorToken` を付ける。** 【決定】
`seatToken` と `spectatorToken` の両方を付けた接続は、どちらとしても扱わずに閉じる。
どちらかを優先すると、観戦のつもりで開いた画面が座席トークンも持っていたときに、黙って手を指せる接続になる。
観戦トークンで座席には就けず、座席トークンでは観戦に入れない。

サーバ → 観戦者

| `t`               | 中身                                      | 意味                           |
| ----------------- | ----------------------------------------- | ------------------------------ |
| `spectator-sync`  | `stateVersion`, `view`, `clock`, `seats`  | 局面一式。繋いだ直後と `hello` |
| `spectator-delta` | `stateVersion`, `events`, `view`, `clock` | 1 手が適用された               |
| `spectator-ended` | `matchResult`, `outcome`, `view`          | 対戦が終わった。送ったら閉じる |

`seats` は座席ごとの表示名とレーティングで、**公開 id を含めない。** `matchId` も渡さない。
観戦トークンは座席の外へ配られる値なので、それを持つだけで対局ログと人を結び付けられる形にしない。

**観戦者へは seed を明かさない。** `ended` が座席へ seed を明かすのは、指した本人が
シャッフルの公正さを確かめるためである（6.4 節）。seed からは両者のデッキの中身がすべて割れ、
それは済んだ対戦でも本人にしか見せないもの（6.6 節）なので、観戦者の `spectator-ended` には載せない。
照合に使わないので、`seedCommit` も渡さない。

観戦者から受けるのは `hello`（局面の取り直し）と `ping` だけである。`move` と `concede` には
`error` を返し、接続は切らない。

**観戦者の数に上限を置く。1 対戦に 32、サーバ全体で 1,024 とする。** 【決定】
観戦者 1 人ぶん、1 手ごとにフルの `view`（平均 5.1 KB、3.2 節）を 1 通送る。観戦トークンを知る 1 人が
接続を積むだけで、その対戦の 1 手ごとの送信がいくらでも膨らむ。1 対戦の上限だけでは、
自分で対戦を開いて観戦者を積むことを対戦の数だけ繰り返せるので、全体にも置く。
座席と違って観戦は断っても誰も負けないので、溢れたら `error` を 1 通送って閉じる。
**決着を伝えたら、観戦者の接続はサーバから閉じる。** 数から外すだけで開いたままにすると、
対戦を開いて観戦者を積んでは終わらせることを繰り返すだけで、上限に数えられない接続が溜まる。

全体の上限は 1 人で使い切れる。自分で開いた対戦に観戦者を積めば、ほかの対戦の観戦を断らせられる。
送信元ごとの上限は置いていない。止まるのは観戦だけで、対戦は止まらないためである。

参照クライアントは `/?watch=<spectatorToken>` を観戦の画面として開く。
**この画面はプレイヤーを作らない。** プレイヤーを消す道は無い（7.2 節）ので、
リンクを開いただけの人のぶんが残り続ける。

## 4. 情報の秘匿

### 4.1 座席ごとの payload 【決定】

1 手ごとに、サーバは座席 `p` について次の 3 つを作る。これ以外の値を座席へ出さない。

```
view       = playerView(state, p)
events     = projectEvents(appliedEvents, p)
legalMoves = (手番側 === p) ? legalMoves(state) : null
```

`legalMoves` を手番側にだけ送るのは帯域の話ではない。手番側の合法手には
その人の手札の `defId` が現れる（`PlayBasic` の `cardInstanceId` が指す先）ので、
相手へ送ると手札が割れる。

観戦者について作るのは次の 2 つで、合法手は無い（3.6 節）。観戦者はみな同じ値を受けるので、1 手に 1 度だけ作る。

```
view   = spectatorView(state)
events = projectEvents(appliedEvents, "spectator")
```

### 4.2 漏洩は機械で検査する 【決定】

自己対戦の全局面で、座席 `p` 向けの payload を JSON 化した文字列が、
`p` から見て隠れているカードのインスタンス ID を 1 つも含まないことを検査する。
隠れているカードとは、相手の手札・両者の山札・両者のサイド（オモテのサイドを除く）にある個体である。

コアには `checkNoLeak`（隠れたゾーンをかき混ぜても合法手が変わらない）と
`checkChoiceVisibility`（`Choice` の候補と payload が owner の見えるゾーンに限る）が既にある。
この検査はそれらの外側、**配信される payload そのもの**に掛ける。
コア §9.1 が「射影を必ず通す規律はサーバ側の責務」と書いた部分を、機械で守る形にしたものである。

観戦者向けの payload にも同じ検査を掛ける。観戦者から隠れているカードには、両者の手札が入る。

**イベントにも掛ける。** 規則は「宛先から見て、手を適用する前も後も正体の分からないカードが、
その宛先へ配るイベントに載らない」である。座席と観戦者の 3 つの宛先すべてについて見る。
公開ゾーンを通ったカード（トラッシュから山札へ戻すなど）は、その時点で正体が見えているので対象にしない。
`cards-revealed` のうち、両者へ見せるものと宛先本人へ見せるものは、見せることが効果の目的なので除く。

**`view` だけを見ていた間、ウラのサイドを取った `prize-taken` が相手へ手札の 1 枚を割っていた。**
取ったカードは手札へ入るのに、イベントがそのカードをそのまま運んでいた。`view` の検査はこれを
通していた。射影はエンジンの側で直した（コア §9.4）。

## 5. デッキ

### 5.1 提出と検証 【決定】

対戦を開く前に、各座席が `defId` の配列を提出する。サーバは次を順に検査し、1 つでも違反があれば対戦を開かない。

1. 60 枚ちょうどである。
2. 同じ名前のカードが 5 枚以上無い。基本エネルギーはこの制限の外に置く。
3. ACE SPEC のカードが 2 枚以上無い（`isAceSpec` が真のカードの合計が 1 枚以下）。
4. たねポケモン、または対戦準備でバトル場に出られる特性を持つカードを 1 枚以上含む（`createGame` が同じ検査を持つが、対戦が開いたあとに例外で落ちるのを避けるため先に見る）。
5. すべての `defId` が実装済みである（`assertDeckImplemented`）。

名前の照合は正規データの `name` を使う。版（`prints`）が違っても名前が同じなら合計で数える。

**カードの識別子をこのリポジトリへ書き込まない。** 【決定】
参照クライアントとテストが使うサンプルデッキは、登録済みのカードから実行時に組む
（`src/sample-deck.ts`）。固定のデッキ表を持つと、カードの識別子がこのリポジトリの
履歴へ入る。カードの定義はすべてエンジンの側にあり、この層が持つのは
「何を満たせばデッキか」だけで足りる。

**レギュレーションマークによるスタンダードの判定は、この層では行わない。** 【決定】
正規データ（`data/cards.generated.json`）はマークの欄を持たず、収録そのものが
スタンダードの範囲を表している。ローテーションは取り込みの側が落とすことで表す。
この層でマークを見ようとすると、データに無い値を持つことになる。

### 5.2 未実装のカードを含むデッキ 【決定】

検査 5 で弾き、**どの `defId` が未実装かを返す。** 黙って落としたり、代替で置き換えたりしない。
`listUnimplementedDefIds` の戻り値をそのまま数えると、実際に人が組もうとしたデッキでの
未実装の出現回数が得られる。これは `docs/design/card-data-foundation.md` の
「読み込まれたデッキから遅延的に積み上げる」運用が要求する計数そのものである。
**人間の対戦環境は、その計数を実データで供給する最初の場所になる。**

### 5.3 名前からの解決 【決定】

人は `defId` ではなくカードの名前でデッキを書く。**名前から `defId` は一意に決まらない。**

実測（`927b661` の正規データ）。

|                             |                                    |
| --------------------------- | ---------------------------------- |
| 定義                        | 2,175 件                           |
| 名前                        | 1,470 種                           |
| `defId` が 2 つ以上ある名前 | 455 種（定義 1,160 件、53.3%）     |
| 1 つの名前の最大            | 34 通り                            |
| 重複の内訳                  | ポケモン 452 種、トレーナーズ 3 種 |
| 基本エネルギー              | 8 種すべて一意                     |

重複のほとんどはポケモンである。同じ名前でも HP もワザも進化段階も違う**別のカード**なので、
**推測で 1 つ選んではならない。** 選ぶと、例外も出ないまま別のデッキで対戦が始まる。

- 解決できない行は、**行番号と理由をつけて全部返す。** 1 件目で打ち切らない。
- 同じ名前が複数あるときは、候補を返して拒否する。候補には、同じ名前のカードを見分ける値（HP・タイプ・ワザの名前・収録など）を添える。
  人はそれを見て 1 つ選び、行のうしろに `defId` を書き足す。
  収録はいちばん新しいものを出す。再録の多いカードは、古い収録では見覚えが無い。
- 名前と `defId` の両方が書かれていて食い違うときは、どちらが本意か分からないので拒否する。
- **読み飛ばす語を持たない。** 見出しの行はカード名として解決できず `unknown-name` になる。
  カードの語彙をこのリポジトリへ書き込まないための選択である（`README.md`）。

参照クライアントは、この文字列を主な入口にしない。`GET /api/cards` の表（候補と同じ値を持つ）から
名前・ワザ・収録で検索させ、人が押した `defId` をそのまま積む。組む時点で 1 枚ずつ選ぶので、
曖昧な名前がそもそも生じない。文字列の解決は、手元のリストを貼って読み込む道として残す。

解決は提出の時点で 1 度だけ行い、**そこから先は解決済みの `defId` 列だけを唯一の情報源とする。**
対局ログに残るのもこの列で、順序も情報源の一部である（§6.2）。インスタンス ID がデッキ配列の添字
（`p{プレイヤー}-{添字}`）である以上、同じ 60 枚でも並びが違えば別の対戦になる。

短い文字列から巨大な配列を作れないよう、行数と 1 行の枚数に上限を置く。

## 6. 対局ログ

### 6.1 唯一の情報源は seed と move 列である 【決定】

1 対戦につき 1 レコード。局面もイベントも保存しない（S-4）。

実測（一様ランダムの自己対戦 20 局、`cardpool` の構成）。

| 保存する形                                | 1 局あたり |
| ----------------------------------------- | ---------- |
| seed ＋デッキ 2 つ＋ move 列（生の JSON） | 12.2 KB    |
| 同（gzip）                                | 0.63 KB    |
| 参考: 全イベントを保存した場合の生の JSON | 115 KB     |
| 参考: 1 局面の `GameState` の JSON        | 9.1 KB     |

イベントを保存すると 9 倍、局面列を保存すると 3 桁膨らむ。いずれも再生で作り直せる値である。

### 6.2 レコードの形 【決定】

```jsonc
{
  "schemaVersion": 3,
  "matchId": "...",
  "engine": {
    "commit": "...", // ビルドのときに git から（§8）。無ければ "unknown"
    "cardDataSha256": "...", // data/cards.generated.json のハッシュ
    "replaySchemaVersion": 3,
  },
  "seed": "9b1c7f0a4e2d6835a1f094c73b2e5d68", // 16 進 32 桁（§6.4）
  "seedNonce": "...", // §6.4 の公開検証用
  "seedShares": ["...", null], // 座席のシェア。どちらもシェアを出さなかった対戦では欄ごと省く（§6.4）
  "seedShareCommits": ["...", "..."], // 参加のときに受け取ったシェアのコミット
  "firstPlayer": 0,
  "decks": [{ "cards": ["..."] }, { "cards": ["..."] }],
  "seats": [
    { "playerId": "...", "displayName": "..." },
    { "playerId": "...", "displayName": "..." },
  ],
  "startedAt": "2026-09-21T07:00:00.000Z",
  "endedAt": "2026-09-21T07:23:11.000Z",
  "moves": [
    {
      "move": { "type": "PlayBasic", "player": 0, "...": "..." },
      "elapsedMs": 4210,
      "source": "human",
      "candidates": 7, // そのときの legalMoves の数
      "chosen": 3, // その中での位置
      "offered": null, // 画面が見せた位置。全部見せたなら null
    },
  ],
  "outcome": { "winner": 0, "reason": "prizes-taken" },
  "matchResult": { "kind": "normal", "winner": 0 },
}
```

**`elapsedMs` を 1 手ごとに持つ。** 【決定】
人がその手に掛けた時間は「この局面は難しい」という無料のラベルであり、
自己対戦では絶対に手に入らない量である。エンジンは時刻を触らない（S-5）ので、
この値を持てるのはログだけである。

**`source` を 1 手ごとに持つ。** 【決定】
値は `human` のみを想定するが、欄を先に置く。将来ここに `bot` が混ざったとき、
欄が無ければ人間の手と見分けられないログが積み上がったあとで気付くことになる。

**`candidates` と `chosen` を 1 手ごとに持つ。** 【決定】
どちらも再生で作り直せる値なので、学習のために持つのではない。**持つ理由は照合である。**
エンジンを直すと合法手の集合が変わりうるが、記録した手が新しい集合にも入っていれば、
§6.4 の検査 1 は黙って通る。同じ手順で別のゲームを再生していても気付けない。
数と位置を突き合わせれば、影響を受けた対戦を機械が挙げられる。

**`offered` を 1 手ごとに持つ。** 【決定】
`legalMoves` は規則が許す手を全部返すが、画面が全部見せるとは限らない（畳む、隠す、
上位だけ見せる）。そのとき人は `legalMoves` とは別の集合の上で選んでいる。
**これは再生で作り直せない唯一の値である。** 記録しないまま学習へ渡すと、
「人がこの手を選ばなかった」という事実を、見せてもらえなかっただけの手についても学ぶ。
値はクライアントの自己申告で、手を受理するかどうかの判断には一切入らない。
全部見せたなら `null` に畳む。参照クライアント（`public/`）は合法手を全部ボタンにするので常に `null` である。

**`firstPlayer` は導出値であって、再生の入力ではない。** 【決定】
`createGame` は `config.firstPlayer` が未指定のときだけコイントスを 1 回引く。
この 1 回が乱数列を進めるので、**コイントスが出したのと同じ先攻を明示で渡しても、
そこから先のシャッフルが全部ずれる。** サーバは `firstPlayer` を渡さない。
ログの `firstPlayer` はイベント `game-started` から読んだ結果で、再生はこれを突き合わせて確かめる。
先攻をロビーや人の選択で決める仕組みを足すなら、「どちらの道で決めたか」を
レコードへ足し、再生も同じ道を通すこと。

**`outcome` と `matchResult` を分けて持つ。** 【決定】
`outcome` はエンジンの `GameOutcome` そのもの（投了と時間切れでは `null`）、
`matchResult.kind` は `normal` / `concede` / `timeout` のいずれかである（§2.3）。
学習が使えるのは `moves` を最後まで再生できる対戦だけで、その判定はこの 2 つの組で決まる。

### 6.3 エンジンの同一性 【決定】

`cardDataSha256` の不一致は**再生を拒否する**。カードの定義が変われば同じ `defId` が別のカードを指しうる。
`commit` の不一致は**警告にとどめる**。エンジンの修理は挙動を変えるが、変えるのは踏んだ対戦だけであり、
踏んだかどうかは再生すれば必ず分かる（非合法手として止まるか、`outcome` が食い違う）。
版を理由に一律で捨てると、直した誤りに触れていない大多数の対戦まで失う。

`commit` はビルドのときに求める（§8）。submodule に commit していない変更があれば、末尾に `-dirty` を付ける。
その記録は、どの commit を用意しても同じエンジンにならない。

### 6.4 再生と検証 【決定】

ログ 1 行から `createGame` をやり直し、`moves` を順に `applyMove` へ通す再生器を持つ。
再生器は 4 つを確かめる。

1. すべての手が、その時点の `legalMoves` に含まれる。
2. 再生の終端の `outcome` がログの `outcome` と一致する。
3. 自己対戦が掛けている不変条件（`src/testing/invariants.ts`）が全局面で成り立つ。
4. 先攻と、各手の `candidates` / `chosen` が記録と一致する（§6.2）。

4 が要るのは、1 だけでは足りないからである。手が新しい合法手にも入っていれば 1 は通るが、
集合そのものが変わっていれば、同じ手順で別のゲームを再生したということである。
**種の読み方が変わる前の版は、再生そのものを断る。** 版 2 までの `seed` は 32 ビットの数値で、
128 ビットになった乱数は同じ値から別の列を出す。走らせれば 0 手目から非合法手として止まるが、
初期盤面だけは誤りを出さずに描けてしまい、読む人には別のシャッフルだと分からない。
断る境目は `OLDEST_REPLAYABLE_SCHEMA_VERSION` に置く。**欄が増えただけでは上げない。**
上げるのは、それより前の記録が別の対戦を再生してしまうときだけである。

**この再生は、ログの健全性の検査であると同時にエンジンの検査である。**
人間の対局は一様ランダムの自己対戦が踏まない筋を踏む。
`docs/roadmap-engine-completion.md` が「未知の誤りを測る手立て」として並べているものに、
実際の対戦という標本が 1 つ加わる。

サーバが `seed` をあとから言い換えていないことは、コミットと公開で示す。サーバは 256 ビットの
乱数 `seedNonce` を引き、**同じ `nonce` に別々の接頭辞を付けた** SHA-256 から 2 つを導く。

```
seed   = sha256("seed:"   + seedNonce) の先頭 16 バイト（16 進 32 桁）
commit = sha256("commit:" + seedNonce)
```

対戦の開始時に `commit` を両者へ渡し、終了時に `seedNonce` を公開する。受け取った側は上の 2 行を
やり直せば、渡された `commit` と、ログの `seed` の両方を検算できる。**接頭辞まで仕様に書くのは、
書かなければ外から検算できないからである。**

接頭辞を分けるのは、コミットが満たすべき 2 つを `seed` の幅から切り離すためである。
対戦の前にサーバを `seed` へ縛ること（拘束）と、対戦中は `seed` を何も明かさないこと（秘匿）。
128 ビットになったいまは `seed` を直接コミットしても総当たりでは開かないが、
分けておけば、`seed` の作り方を次に変えたときにこの性質を数え直さずに済む。

**サーバが対戦の前に `nonce` を引き直して並びを選ぶことは、座席のシェアで防ぐ。**
コミットだけで示せるのは「あとから言い換えていないこと」までで、`nonce` を引くのが
サーバだけなら、引き直して有利な並びを選べる（grinding）。そこで座席にも値を出させ、
**その値をサーバが知る前に、サーバを `nonce` に縛る。**

1. 参加（`/api/join`）のとき、座席は 32 バイトの乱数 `share` を引き、`sha256("share:" + share)` だけを送る。
2. 席が決まると、サーバは `nonce` を引き、`commit` と両座席のシェアのコミットを、座席の割り当て（7.1 節）に載せて両座席へ渡す。
3. 座席はそれを受け取ってから `/ws` に `seedShare` を付けて繋ぎ、シェアを開く。コミットと合わないシェアは受け取らない。
4. コミットを送った座席がみな開いたら `seed` を決め、対戦を始める。それまで局面も時計も無い。

```
seed = sha256("seed:" + seedNonce + ":" + share0 + ":" + share1) の先頭 16 バイト
```

開かなかった座席の `share` は空文字列にする。どちらの座席もシェアを出さなかった対戦では
上の `seed:` + `seedNonce` の式のままにし、シェアを持たない記録と同じ読み方で検算できるようにする。

この順なら、サーバは `nonce` に縛られた時点で、並びを決める値の一部を知らない。座席の側も、
相手のシェアは開く前にコミットされているので、相手の値に合わせて自分の値を選べない。
サーバと片方の座席が組んでも、もう片方のシェアを知らないまま両方が縛られる。

**開かない座席は、30 秒で待つのをやめる。** 期限を見るのは持ち時間と同じ定期処理なので、
実際に始まるのはその間隔ぶん遅れうる。 シェアを null として対戦を始め、その座席の時計は
そこから流れる（3.4 節）。待ち続けると、来ない相手を待つ人が対戦を始められない。
選ぶ余地はここに残る。開くかどうかを選べる座席は、並びを 2 通りから選べる。サーバが
届いたシェアを「期限に遅れた」として捨てても同じで、合わせても 4 通りを越えない。
引き直しのように好きなだけ選べるわけではない。シェアが使われなかったことは、両座席の画面が
決着のあとに出す。シェアを捨てられた座席は「自分のシェアが使われていない」と、その相手は
「相手のシェアが使われていない」と出す。値の対応が合っていても、黙って「合う」とだけは出さない。

**検算するのは座席の画面である。** `ended` に `seedNonce` と `seedShares` を載せ、画面は
シェアを開く前に受け取った `commit` とシェアのコミットに、開かれた値が合うかを確かめる。
サーバが後から送る値同士を比べても、シェアごと差し替えられていれば辻褄は合ってしまう。
座席の割り当てに載ってきた自分のコミットも、自分が送ったものと見比べる。すり替えたコミットに
合う値を自分のシェアとして開かれると、ほかの突き合わせは全部通るからである。
画面が確かめられるのは値の対応までで、その `seed` で対局したことは記録の再生（上の 4 つ）で確かめる。
記録にもシェアとそのコミットを残し、再生器はシェアをコミットと突き合わせてから `seed` を導き直す。

シェアを出すかどうかは座席が決める。参照クライアントは `crypto.subtle` が使えるとき
（https か localhost）にだけシェアを出す。出さなかった座席のぶんは、サーバと相手の値で並びが決まる。

### 6.5 保存先 【決定】

**対局ログそのものは R2 に置く。** 1 局を 1 つのオブジェクト（`matches/<終わった日>/<matchId>.json`）にし、
中身は JSONL の 1 行と同じ形にする。日付は `endedAt` の UTC の日である。取ってきて並べればそのまま JSONL になり、
`tools/replay-verify.ts` はディレクトリごと読める。学習は先頭から順に読むだけである。
1 局はおよそ 9 KB（圧縮しない）で、R2 の無料枠 10 GB に 100 万局ほど入る。

**読み出しのための索引を D1 に置く**（`matches` 表）。索引が持つのは記録から導いた値だけで、
**消しても対局ログは失われない。** 対局ログそのものを D1 へ移すのは別の話で、これはその一歩ではない。

**索引に行があることは、その対戦をレーティングへ入れ終えたことも表す。** 行を足すのと
レーティングを動かすのを 1 つのトランザクションで行うので、片方だけが残ることはない。
座席のプレイヤーが D1 に無ければ、レーティングは動かさずに行だけを足す。入れる相手がいない対戦を、
起きるたびに入れ直そうとしないためである。

終わった対戦は、次の順で残す。1 局ずつ順に並べる。レーティングは前の対戦を入れた値から次を計算するからである。

1. R2 へ書く。**書けなければそこで止め、レーティングを動かさない。** レーティングは対局ログから
   作り直せる、というのが 7.2 節である。記録に無い対戦でレーティングだけ動かすと、どこから来た差か誰にも言えなくなる。
2. 索引とレーティングを 1 つのトランザクションで D1 へ入れる。

2 で落ちた対戦は、R2 にだけある状態になる。**Durable Object が起きたときに R2 と索引を突き合わせ、
索引に無い対戦を入れ直す。** 見るのは前回済ませた日付から先だけで、済んだ日付は 2 日の余裕を持たせて覚える
（`archive_state` 表）。書いている途中で Durable Object が入れ替わると、前の日付の対戦があとから届きうるからである。
入れられなかった対戦が残れば済んだ日付を進めず、次に起きたときにもう一度同じ日付から見る。
一覧を取るあいだは 1 局ずつの列に並ばない。並ぶと、起きた直後の要求がその間ずっと待たされる。

入れ直した対戦のレーティングは、**入れ直した時点の値から計算する。** そのあいだに後の対戦が先に入っていれば、
記録を終わった順に並べて作り直した値とはずれる。起きるのは D1 へ書けなかったときだけなので、ずれを受け入れる。

**索引は信じきらない。** 引いた識別子と、読めた記録の識別子が違えば渡さない。
起きないのが普通だが、起きたときに出るのは「読めない」ではなく**頼んだのとは別の対戦の盤面**なので、
読めたことを根拠にしない。

D1 の表は Durable Object が起きたときに作る。表の形の版を `schema_version` 表に持ち、足りない段だけを当てる。
`wrangler` のマイグレーションを別に回さずに済む。

### 6.6 リプレイ 【決定】

**読めるのは自分が指した対戦だけである。** 他人が指した対戦は、存在しない対戦と同じ「無い」を返す。
デッキと引きが誰にでも見えるなら、対戦環境として成り立たない。

終わった対戦は、**当人どうしには両座席ぶんを見せる。** 相手の手札も山札の枚数も出す。
終わっている以上そこに隠す利益はなく、負けた理由を読み返せることのほうが要る。
それでも §1 の S-2 は動かない。外へ出るのは `playerView` と `projectEvents` を通った値だけで、
山札とサイドの**並び**は終わった対戦でも誰にも渡さない。

1 手ぶんの局面は、`createGame` から `ply` 手まで `applyMove` を掛けて作る。
1 局まるごと辿り直しても 50〜65 ミリ秒である（§6.1）。手数は整数に丸める。
丸めずに返すと、盤面は 2 手目の後なのに応答には 1.5 と書いてあることになる。

リプレイは 1 手ごとに 1 局を引き直す。索引が R2 のキーを持っているので、
読むのはその 1 オブジェクトだけである（§6.5）。**索引を引けることと、その対戦を読めることは別である。**
座席の検査は毎回通す。

**局面のキャッシュをメモリにだけ置く。** 【決定】
置かないと、1 手進めるたびに初手から指し直すことになる。同期で走るので、
そのあいだ進行中の対戦の手も持ち時間のスイープも止まる。置くのは、最後に描いた局面と、
16 手ごとのチェックポイントである。進むときは最後の局面から、戻るときは手前のチェックポイントから指す。
実測（249 手の 1 局を 1 手ずつ辿る）で、1 フレームあたり 11.8 ミリ秒から、進むときは 0.30 ミリ秒、
戻るときは 1.07 ミリ秒になった。覚えておくのは直近に読まれた 32 局までで、全部辿ったときで 11.5 MB である。

局面を保存しない決め（§6.1）は変えない。唯一の情報源は seed と手の列のままで、キャッシュは消えても
作り直せる。**キーは対戦 ID ではなく、盤面を決める中身（seed、デッキ、手の列）のハッシュにする。**
対戦 ID で引くと、同じ ID で中身の違う記録に、前に読んだ別の記録の盤面を返しうる。
読む人にはそれが別の対戦だと分からない（§6.5 の索引で同じ形の危険を踏んでいる）。
記録された手が指せなかった地点（下記）もキャッシュに持ち、そこから先は指さない。

リプレイにも §6.3 の同一性の規律を通す。`cardDataSha256` が違う記録は**リプレイを断る**。
同じ `defId` が別のカードを指しうるので、そのまま再生すると誤りを出さずに違う盤面を見せる。
`commit` の違いは**警告を付けて読ませる**。版を理由に一律で捨てると、直した誤りに触れていない
大多数の対戦まで読めなくなる。

だから、**記録された手は指す前にいまの合法手と突き合わせる。** 版が違えば、記録された手が
合法でなくなりうる。そのまま `applyMove` へ渡すとエンジンが投げ、エンドポイントはその例外メッセージをそのまま
外へ出すことになる。読む人に意味が無いうえ、その対戦は食い違う地点より先へ進めなくなる。
合わなくなった地点で止め、**どこから先が再現できないかを返して、手前までは読ませる。**
再生器（`src/replay.ts`）が同じ地点を `illegal-move` として記録して止まるのと同じ規律である。

局面には、**その手を指す直前の盤面も添える。**
手の見出しは出したカードの名前で読むが、指したあとの手札にそのカードはもう無い。
画面が 1 手戻った局面を取り直すと往復が倍になるので、サーバが一緒に返す。
添えるのも射影を通った値である。

## 7. 相手を見つける

### 7.1 マッチング 【決定】

2 つだけ持つ。

- ルームコード。同じ文字列を入れた 2 人を繋ぐ。
- マッチングキュー 1 本。先に待っていた 2 人を繋ぐ。

**同じプレイヤーは 1 つしか待たせない。** 新しく入ってきたら、そのプレイヤーが待っているものを先に降ろす。
別のタブを開いたり待っている間に読み込み直すと、同じプレイヤーが両側に座り、
自分と自分の対戦が 1 局として記録に残って、そのプレイヤーに 1 勝 1 敗が付く。

降りたチケットは、**待っているチケットと区別して答える。** 同じ応答にすると、降ろされた側のタブは
「相手を待っています」のまま永久に問い合わせ続ける。引き換えに来たチケットの行方は
「席が取れた」「まだ待っている」「もう終わっている」「降りている」「知らない」の 5 つである。

**終わった対戦と、降りたチケットは別である。** 席が決まったあと、取りに行く前に相手が投了するか
時間切れになると、席そのものはもう無い。これを「降りている」と同じ応答にすると、
「別のタブから入り直した」という嘘を出すことになる。その人は 1 手も指していないが、
プレイヤーとしては数えられていて、レーティングも動き、記録も残っている。読み返せる対戦がある以上、
そう答える。

**引き換えに来ても、座席を消さない。** 1 度読んだら消す作りだと、その応答が回線の不調で
落ちたときに、次に取りに来た人へ「もう降りている」と答えることになる。対戦のほうは
始まっているので、その人は座らないまま時間切れで負け、記録には普通の負けとして残る。
チケットそのものが引き換えの鍵なので、同じチケットで何度取りに来ても同じ座席を返す。
引き換え待ちの座席は、その対戦が終わってレジストリを離れるときに消える。

**席を捨てても、「もう終わっている」とは答え続ける。** 引き換え待ちの座席は数に上限があり、
溢れたぶんは終わった席から捨てる。捨てた席まで「知らない」と答えると、その人はもう一度さがして
2 局目を始めてしまう。1 局目はレーティングを動かしログにも残っているのに、本人はそこへ辿り着けない。
席そのものは捨てても、対戦の識別子だけは残す。

**ストアを書き換えるのは、入れると決まってからである。** 表示名の変更はストアにも
それ以後の対局ログにも残り、取り消せない。デッキで断られた人の名前だけが変わると、
断られた側から見れば何も起きていないのに名前が変わっていることになる。

**レーティング帯で分けない。** 人が少ないうちは待ち時間が伸びるだけである。

**座席の割り当てには、サーバのコミットと両座席のシェアのコミットを載せる**（6.4 節）。座席はこれを
シェアを開く前に受け取り、決着のあとの検算に使う。シェアが開くのを待っている対戦も、
引き換えには「席が取れた」と答える。席はもう決まっていて、あとは繋ぐだけだからである。

**知らないチケットと、降ろしたチケットは別である。** ロビーはメモリにしか無いので、入れ替えればチケットは
全部知らないものになる。これを「降りている」と答えると、タブを 1 つしか開いていない人に
「別のタブから入り直した」と言うことになる。覚えていられる数を超えたぶんも同じ扱いにする。
タブの側は、「まだ待っている」以外の答えでは待つのをやめる。知らない形の答えを受け取っても
待ち続けないためである（入れ替えのあと、古いタブが新しい答えを受け取ることがある）。

### 7.2 プレイヤーとレーティング 【決定】

**持つ理由は対戦の体験ではなく、記録である。** 人の手を真似て学ぶとき、打った人の強さは
最も効く共変量になる。そして**座席と人をあとから結び直すことはできない**ので、
対戦の時点で持っていなければ、その対戦には二度と付けられない。だから、ログを貯め始める前に入れる。

**人を特定できる値を持たない。** 置くのは 3 つだけである。

| 置くもの               | なぜ                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| サーバが発行した識別子 | 対戦をまたいで「同じ人か」を言うため。対局ログに残るのはこれである |
| 本人が付けた表示名     | 画面に出すため。本人確認ではないので、長さと制御文字だけ見る       |
| レーティングと戦績     | 「どのくらい強いか」を言うため                                     |

メールアドレスもパスワードも置かない。学習に要るのは「同じ人か」と「どのくらい強いか」の
2 つだけで、それ以上は集めない。**公開リポジトリで動かす以上、置かずに済むものは置かない。**

認証はシークレット 1 本である。作ったときに 1 度だけ返し、**サーバは控えを持たない**
（照合はハッシュで行う）。失うとその戦績には戻れない。
**公開の識別子とシークレットは別の値にする。** 同じ値にすると、対局ログがシークレットの一覧になる。

**プレイヤーを作る速さに上限を置く。** 消すエンドポイントが無いので、作られたぶんは残り続ける。
増えるのは D1 の行で、無料枠の書き込み回数もそのぶん食われる。遮断ではなく減速にする。同じ送信元の向こうに何百人も
いることがあり（携帯の回線、学校、職場）、初めて来た人はここで作るためである。
超えたときは `429` と `too-many-accounts` を返す。

**送信元は Cloudflare が付ける `CF-Connecting-IP` で見分ける。** 送り手が同じ名前の要素を書いても
Cloudflare が上書きする。`x-forwarded-for` は送り手が好きに書ける値なので見ない。
上限は既定で掛ける（1 つの送信元から続けて 20 回、そのあとは 10 秒ごとに 1 回）。`ACCOUNT_BURST` で回数を変えられ、
`0` で外れる。**読めない値では既定に倒す。** 書き損じ 1 つで上限が黙って外れないようにするためである。

レーティングは Elo で、初期値 1500、係数 24 とする。投了と時間切れも普通の勝敗として数える。
規則上の敗北条件ではない（§2.3）ことは対局ログの `matchResult` が区別して持っているので、
レーティングの側で分ける必要はない。**レーティングは勝敗の履歴であって、学習の終端報酬ではない。**

対局ログの `seats` に残すのは、**対戦を始めた時点のレーティング**である（§6.2）。
終わったあとのレーティングは対戦の並びから導けるので持たない。

保存先は D1 の `players` 表で、シークレットはハッシュだけを持つ。対戦サーバはよく使う 4,096 人ぶんを
メモリに持ち、変えたときは D1 へもすぐ書く。**D1 との読み書きは 1 本の列に並べる。** 読み直しが前に出した書き込みを
追い越すと、古いレーティングがメモリへ戻る。読み直した値で、メモリにある新しい値を上書きしない。

## 8. エンジンの取り込み方 【決定】

エンジンは git submodule（`engine/`）として取り込む。npm の依存にはしない。

npm の依存にするには、エンジン側に手を入れる必要がある。エンジンの `package.json` は
`main` が TypeScript の `src/index.ts` を指し、`exports` も `types` も持たず、
`prepare` はビルドではなく git hook の設定である。ビルド（`tsconfig.build.json`）は
型定義を出さず、対象も `src` と `harness` だけである。

決め手は**カードの正規データの読み方**である。エンジンは
`data/cards.generated.json`（2.1 MB）を実行時に読み、その位置を
「自分自身の位置から `package.json` が見つかるまで親をたどる」ことで決める
（`engine/src/cardpool/generated-cards.ts`）。submodule なら `engine/package.json` が
そのまま目印になり、この探索が何も変えずに当たる。

**Worker にはそのファイルが無いので、ビルドのときに中身を埋め込む**（`tools/build-worker.ts`）。
エンジンのコードは変えず、読み込む関数だけを埋め込んだデータを返すものに差し替える。
差し替えが 1 か所も起きなければビルドを止める。エンジン側でファイルの場所が変わったときに、
カードを 1 枚も読めない Worker を出さないためである。
`engine.commit` と `cardDataSha256` もビルドのときに求めて埋め込む。Worker の中には `git` も無い。

**submodule が指す commit は、そのまま対局ログへ記録する `engine.commit` である**（6.3 節）。
再生に使うエンジンの同一性と、依存の pin が同じ 1 つの値になる。

npm パッケージへ移すのは、エンジン側が `exports` と型定義と公開の経路を持ったときとする。
そのときサーバ側で直すのは `src/engine.ts` 1 ファイルである。

## 9. `seed` の幅 【決定】

**塞ぐ前は、対戦中の人が自分の初手だけから `seed` を総当たりで割り出せた。** 割れると自分の
山札の並びとサイドの中身が全部読め、相手のデッキリストが分かっていれば相手の山札の並びも読める。
§4 の射影はこれを防がない。漏れているのは隠したカードの中身ではなく、シャッフルの入力だからである。

このリポジトリで実測して確かめたこと。

| 確かめたこと                                                           | 実測                                                                             |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 自分の手札に出るインスタンス ID は、デッキ配列の添字そのものである     | `playerView` の `self.hand` が `p0-51` のような値を返す                          |
| その添字は相手のデッキに依存しない。攻撃側は自分の情報だけで計算できる | 相手のデッキの並びを逆にしても、自分の初手 7 枚の添字は 3 つの seed すべてで同一 |
| 初手 7 枚の添字は `seed` をほぼ一意に決める                            | 先頭 2,000,000 seed の走査で一致は 1 件                                          |
| 総当たりの速さ（`createGame` をそのまま回す、1 コア）                  | 27,400 seed/s。2^32 全域で約 44 時間                                             |

**44 時間は「`createGame` を丸ごと回した場合」の上限である。** シャッフルだけを書き直せば
桁が変わる。エンジン側は同じ穴を「1 コアで毎秒 224 万件、2^32 の全域が 32 分」と実測している
（`engine/src/rng.ts`）。1 局が数十分続く対人環境では、現実的な脅威だった。

エンジンの `RngState` が uint32 で、`createRng` が `seed >>> 0` だったので、
**サーバ側で強い乱数を使っても 32 ビットに切り詰められていた。**

サーバだけで塞ぐ道もあった。座席へ出すインスタンス ID を対戦ごとの別名にし、さらにデッキを
サーバ側で並べ替えてからエンジンへ渡す。添字から種への手掛かりが断たれるので、この漏れ自体は止まる。
ただしエンジンが引く乱数は 32 ビットのままで、シャッフルの入力の幅は広がらない。
同じ種が別の対戦で二度出ることを、局数が増えたときに数え直すことになる。

**エンジン側を直す道を採った。** `RngState` は 128 ビット（uint32 4 語）になり、
`createRng` は種を ChaCha の核へ通してから状態に置く。`GameConfig.seed` は数値と 16 進文字列の
どちらも受け、文字列なら 128 ビットがそのまま入る。

サーバはこう使う。

- `seed` は 16 進 32 桁の文字列で持つ（§6.2、§6.4）。**数値では渡さない。**
  数値の種は Float64 のビットとして効くので、整数で配れる幅が 2^53 で頭打ちになる。
  2^53 は上の実測でも一万年かかるので総当たりでは開かないが、幅の上限をここで決めてしまう
  理由が無い。
- 種を足し算で組み立てない。自己対戦が `seed + ゲーム番号` で配るような作り方は、
  2^53 を越えた先で隣り合う種が畳まれる。サーバは `nonce` の SHA-256 から導くので、この形を通らない。
- 種の読み方が変わる前に書いたログは、再生を断る（§6.4）。

残っているのは、インスタンス ID がデッキ配列の添字そのものだという性質である。観測できることは
変わっていない。ただし読み解くには `seed` が要るので、**幅が 128 ビットになった時点で、
これだけでは足りなくなった。**

## 10. 未決定事項

- **プレイヤーが増え続けること。** 作る速さには上限を置いた（§7.2）が、止まるのは
  1 か所から機械で回す形だけである。送信元を変えながら来るもの（IPv6 なら 1 人でいくらでも
  変えられる）は止まらないし、待てばいくらでも作れる。止めるには総数の上限か、
  使われていないプレイヤーを消すエンドポイントが要る。**どちらも「どこまでなら消してよいか」の判断が要る。**
  1 局も指していないプレイヤーだけを消すなら取り返しは付くが、その線をどこに引くかは決まっていない。
- **初めて読む対戦の重さ。** 局面のキャッシュを置き、1 手ずつ辿るぶんは軽くなった（§6.6）。
  残るのは、覚えていない対戦の遠い手数を頼まれたときで、1 局まるごと辿り直す（190〜240 手で 25 ミリ秒前後）。
  頼めるのは自分が指した対戦だけだが、覚えておける 32 局を越える数の対戦を順に頼めば、毎回これを払わせられる。
  速さに上限を置くか、重い再生を対戦サーバの外へ出すかは、そうした使われ方が見えてから決める。
- **複数の Durable Object への分散。** 対戦は 1 つの Durable Object のメモリに載る
  （1 局面 9 KB、1 手 0.2 ミリ秒の実測。Durable Object 1 つのメモリは 128 MB）。
  分散が要る規模に達していない。達したときに、対戦を部屋ごとの Durable Object へ分けるか、
  局面を外へ出すかを決める。
- **生きている対戦は、Durable Object が入れ替わると消える。** デプロイのときと、Cloudflare が
  入れ替えたときに起きる。自動のデプロイは指している対戦が無くなるまで待つ（`docs/deploy.md`）が、
  待つのには上限があり、Cloudflare が入れ替えるときは避けられない。終わった対戦とプレイヤーは D1 と R2 に残る。
  進行中の局面を保存すれば残せるが、1 手ごとの書き込みが無料枠の書き込み回数を食う。
  消えた対戦はレーティングにも記録にも入らない。
- **人間の対局から学習へ渡す形。** 観測と行動の表現そのものは
  `docs/design/ai-training-loop-skeleton.md` 7 節の未決定に属する。この文書は
  「再生できる move 列を残す」ところまでを引き受ける。
