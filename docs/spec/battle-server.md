# SPEC: 対戦サーバ

人間同士のオンライン対戦を成立させ、その対局を AI の学習に使える形で残すための層である。
エンジン（`engine/`、git submodule として取り込んだ `poke-tcg-engine`）の
`docs/spec/engine-core.md`（以下コア SPEC）がスコープ外へ置いた 4 つ、すなわち
対戦サーバのプロトコル、デッキ構築バリデーション、イベント射影の詳細規則（コア §9.2）、
リプレイの永続形式を、この文書が引き取る。

ルールの判定は 1 行もここに書かない。ルールはコアが持つ。

## 0. スコープ

### 対象

- 対戦の進行の権威（サーバが `GameState` を持ち、両者の入力を受けて `applyMove` を呼ぶ）。
- 座席ごとの情報の秘匿。
- 通信のプロトコルと、切断と再接続と持ち時間。
- デッキの提出と検証。
- 対局ログの形式と保存と再生。
- 相手を見つける手立て。

### スコープ外

- 描画（クライアントの見た目）。プロトコルが運ぶ値の形までをこの文書が定め、その先は持たない。
- レーティングとアカウント。§7 に導線だけ置く。
- 学習そのもの。ログの形式までがこの文書で、そこから先は `docs/design/ai-training-loop-skeleton.md`。

---

## 1. 不変条件

コアの C-1 から C-5 を前提に、サーバ側で追加して守る性質である。

- **S-1 権威はサーバが持つ `GameState` にある。** クライアントは盤面もダメージもサイドの枚数も申告しない（コア C-5 の運用側）。クライアントから来る値は「どの手を選んだか」だけである。
- **S-2 クライアントへ出る値は、必ず射影を通る。** `ApplyResult.state` と `ApplyResult.events` をそのまま配信する経路を作らない。座席へ出てよいのは `playerView(state, seat)` と `projectEvents(events, seat)` の戻り値、および**手番側だけへ送る合法手**である。この規律はコア §9.1 が明示的にサーバ側の責務としたものである。
- **S-3 seed は対戦が終わるまで公開しない。** seed はシャッフルを完全に決めるので、対戦中に渡すと相手の山札とサイドがすべて割れる。
- **S-4 対局ログは seed と move 列で足りる。** 局面もイベントも保存しない。コア C-4（同一 seed ＋同一 move 列 → 同一の状態列とイベント列）がこれを保証する。
- **S-5 エンジンへ時刻と通信を持ち込まない。** 持ち時間、切断、投了はすべてサーバの語彙であり、`Move` にも `GameState` にも `WinReason` にも足さない（コア D-3）。
- **S-6 対局ログは、それを作ったエンジンの同一性を刻む。** エンジンを直すと同じ move 列が別の対戦を再生しうる。刻印が無いログは、再生できるかどうかを言えない。

## 2. 対戦の進行

### 2.1 いつでも手を持つのは 1 人である 【決定】

`legalMoves` は、選択待ちがあれば最上段の `Choice` の owner の手だけを、無ければ `state.turnPlayer`
の手だけを返す（コア SPEC §4、§6.4）。**両者が同時に手を持つ状態は存在しない。**
対戦準備の場出しも、きぜつ後の昇格も、相手の番の割り込みも、すべて `Choice` を介して
「そのとき手を持つ 1 人」へ集約される。

したがってサーバは、その時点の手番側を state から導く。座席と手番の対応をサーバ側で別に持たない。

```
手番側 = state.choices.at(-1)?.owner ?? state.turnPlayer   （phase === "gameover" なら不在）
```

### 2.2 手の受理 【決定】

サーバは 1 つの `Move` を受け取るたび、次の順に検査する。順序を入れ替えない。

1. 送信元の座席が手番側であること。違えば `not-your-turn` を返し、state は変えない。
2. 送信された `stateVersion` が現在値と一致すること。違えば `stale-version` を返し、現在の局面一式を送り直す。
3. `legalMoves(state)` に `movesEqual` で一致する手があること。無ければ `illegal-move` を返す。

`stateVersion` は 1 手の適用ごとに 1 増えるサーバ側の整数である。`state.eventSeq` を流用しない
（イベント数は手ごとに飛ぶので、クライアントが次の値を予測できない）。
この検査は二重送信と、古い画面から押された手を、同じ 1 つの仕組みで弾く。

**検査 3 の失敗は対戦を終わらせない。** コア §2.1 は `applyMove` が非合法手に例外を投げると定め、
その例外をエラー応答へ変換する責務を呼び出し側（このサーバ）に置いた。
サーバは `legalMoves` との照合で先に弾き、`IllegalMoveError` が実際に飛んできた場合は
サーバ側の欠陥として記録する（クライアントの責任にしない）。

### 2.3 投了と時間切れは move ではない 【決定】

`Move` に投了を足さない。根拠は 2 つある。

- 投了はルール上の敗北条件ではなく対戦の運用である。`WinReason` の 4 値（`prizes-taken`、`no-pokemon`、`deck-out`、`effect-declared`）はいずれも盤面から導かれる。
- 行動空間に投了を足すと、学習する方策がそれを選べるようになる。**投了を選べる方策は、学習の初期に投了へ収束しうる。** 対戦の都合で行動空間を広げない。

投了と時間切れは、engine の `outcome` とは別の `matchResult` としてサーバが持つ。
ログは両方を持つ（§6.2）。局面としての勝敗が付かないまま終わった対戦では `outcome` が `null` になる。

## 3. プロトコル

### 3.1 通信方式は WebSocket 1 本とする 【決定】

座席ごとに 1 本の WebSocket を張り、その上で JSON のメッセージを双方向に流す。

根拠。この対戦は手番制だが、**片側の入力が他方への出力になる**ので、サーバからの push が要る。
相手の手、持ち時間の進み、相手の切断はいずれもクライアントが問い合わせる性質のものではない。
HTTP のポーリングは遅延と無駄な往復を持ち込み、SSE ＋ POST は接続を 2 本に分けたぶん
座席の生死の判定が 2 箇所に散る。WebSocket なら「接続が生きているか」と「座席が繋がっているか」が一致する。

実装は `ws`（依存 0 個）を使い、socket.io は採らない。独自のフレーミングと再接続層を
持ち込むと、この文書が定めるプロトコルの上にもう 1 段の意味論が乗る。

**待ち合わせ（7 節）は HTTP に載せる。** 【決定】
相手を探す往復は要求と応答で足り、押し出しが要るのは対戦が始まってからである。
待ち合わせまで WebSocket に載せると、対戦のプロトコルに対戦でないメッセージが混ざる。

### 3.2 メッセージ 【決定】

クライアント → サーバ

| `t`       | 中身                   | 意味                             |
| --------- | ---------------------- | -------------------------------- |
| `hello`   | `seatToken`            | 座席に就く。再接続もこれ 1 つ    |
| `move`    | `stateVersion`, `move` | 手を指す（2.2 節の検査を受ける） |
| `concede` | なし                   | 投了する                         |
| `ping`    | なし                   | 生存確認。サーバは `pong` を返す |

サーバ → クライアント

| `t`      | 中身                                                                           | 意味                                                         |
| -------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `sync`   | `matchId`, `seat`, `stateVersion`, `view`, `legalMoves`, `clock`, `seedCommit` | 局面一式。`hello` の直後と、`stale-version` の応答として送る |
| `delta`  | `stateVersion`, `events`, `view`, `legalMoves`, `clock`                        | 1 手が適用された。両座席へ送る                               |
| `reject` | `reason`, `stateVersion`                                                       | 手を受理しなかった。理由は 2.2 節の 3 値                     |
| `ended`  | `matchResult`, `outcome`, `seed`, `seedNonce`, `replayId`                      | 対戦が終わった。ここで初めて seed を明かす（S-3）            |
| `pong`   | なし                                                                           |                                                              |

`legalMoves` は**手番側の座席へだけ**配列を入れ、他方へは `null` を入れる（S-2）。
`view` は `playerView` の戻り値そのもの、`events` は `projectEvents` の戻り値そのものである。
この 3 つを組み立てるのは `src/hub.ts` の `syncFor` と `deltaFor` だけとし、
ほかの経路から座席へ値を送らない。

**`delta` は毎手フルの `view` を運ぶ。差分を送らない。** 【決定】
`playerView` の JSON は実測で平均 5.1 KB、1 局 158 手（一様ランダムの自己対戦での実測値）で
両座席合わせて 1.6 MB になる。差分プロトコルはこの帯域と引き換えに、
「クライアントが持つ盤面」という第 2 の権威を作る。S-1 を機械的に守れるほうを採る。

### 3.3 再接続 【決定】

座席は `seatToken`（対戦の開始時に発行する推測不能な文字列）で同定する。
接続が切れても対戦は終わらず、同じ `seatToken` での `hello` が座席を取り戻して `sync` を受ける。
サーバは局面を持っているので、再接続に特別な復元の手順は要らない。

同じ `seatToken` で 2 本目が繋がったら、古いほうを閉じる。観戦は別の口（`spectatorToken`）とし、
**観戦者には両者の `view` を渡さない。** 対戦中の観戦は、両座席の非公開ゾーンを落とした
第 3 の射影を要する。これは未決定として §8 に置く。

### 3.4 持ち時間 【決定】

座席ごとに「1 手の制限 60 秒」と「持ち時間の貯え 15 分」を持つ。
手番側の 60 秒を越えたぶんが貯えから減り、貯えが尽きた時点でその座席の時間切れ負けとする。

**時間切れで自動の手を指さない。** 【決定】
自動の手は、その人が選んでいない手をその人の座席の名前でログへ混ぜる。
学習の側から見ると、区別できる印を付けたうえで捨てるしかない行が増えるだけである。
時間切れ負けは単純で、ログも汚さない。

**切断そのものには罰を置かない。** 【決定】
切断中も時計は流れる。回線が不安定なだけの人を切断即負けで罰しないこと、
切断を使った引き延ばしが時計に吸収されることが、同じ 1 つの規則から出る。
「切断の猶予時間」という概念を別に作らない。

## 4. 情報の秘匿

### 4.1 座席ごとの payload 【決定】

1 手ごとに、サーバは座席 `p` について次の 3 つを作る。これ以外の値を座席へ出さない。

```
view       = playerView(state, p)
events     = projectEvents(appliedEvents, p)
legalMoves = (手番側 === p) ? legalMoves(state) : null
```

`legalMoves` を手番側にだけ送るのは帯域の話ではない。手番側の合法手には
その人の手札の `defId` が現れる（`PlayBasic` の `cardInstanceId` が指す先）ので、
相手へ送ると手札が割れる。

### 4.2 漏洩は機械で検査する 【決定】

自己対戦の全局面で、座席 `p` 向けの payload を JSON 化した文字列が、
`p` から見て隠れているカードの個体番号を 1 つも含まないことを検査する。
隠れているカードとは、相手の手札・両者の山札・両者のサイド（オモテのサイドを除く）にある個体である。

コアには `checkNoLeak`（隠れたゾーンをかき混ぜても合法手が変わらない）と
`checkChoiceVisibility`（`Choice` の候補と payload が owner の見えるゾーンに限る）が既にある。
この検査はそれらの外側、**配信される payload そのもの**に掛ける。
コア §9.1 が「射影を必ず通す規律はサーバ側の責務」と書いた部分を、機械で守る形にしたものである。

## 5. デッキ

### 5.1 提出と検証 【決定】

対戦を開く前に、各座席が `defId` の配列を提出する。サーバは次を順に検査し、1 つでも破れたら対戦を開かない。

1. 60 枚ちょうどである。
2. 同じ名前のカードが 5 枚以上無い。基本エネルギーはこの制限の外に置く。
3. ACE SPEC のカードが 2 枚以上無い（`isAceSpec` が真のカードの合計が 1 枚以下）。
4. たねポケモン、または対戦準備でバトル場に出られる特性を持つカードを 1 枚以上含む（`createGame` が同じ検査を持つが、対戦が開いたあとに例外で落ちるのを避けるため先に見る）。
5. すべての `defId` が実装済みである（`assertDeckImplemented`）。

名前の照合は正規データの `name` を使う。版（`prints`）が違っても名前が同じなら合計で数える。

**カードの識別子をこのリポジトリへ書き込まない。** 【決定】
参照クライアントと試験が使う見本のデッキは、登録済みのカードから実行時に組む
（`src/sample-deck.ts`）。固定のデッキ表を持つと、カードの識別子がこのリポジトリの
履歴へ入る。カードの定義はすべてエンジンの側にあり、この層が持つのは
「何を満たせばデッキか」だけで足りる。

**レギュレーションマークによるスタンダードの判定は、この層では行わない。** 【決定】
正規データ（`data/cards.generated.json`）はマークの欄を持たず、収録そのものが
スタンダードの範囲を表している。ローテーションは取り込みの側が落とすことで表す。
この層でマークを見ようとすると、データに無い値を持つことになる。

### 5.2 未実装のカードを含むデッキ 【決定】

検査 5 で弾き、**どの `defId` が未実装かを返す。** 黙って落としたり、代替で置き換えたりしない。
`listUnimplementedDefIds` の戻り値をそのまま数えると、実際に人が組もうとしたデッキでの
未実装の出現回数が得られる。これは `docs/design/card-data-foundation.md` の
「読み込まれたデッキから遅延的に積み上げる」運用が要求する計数そのものである。
**人間の対戦環境は、その計数を実データで供給する最初の場所になる。**

### 5.3 名前からの解決 【決定】

人は `defId` ではなくカードの名前でデッキを書く。**名前から `defId` は一意に決まらない。**

実測（`927b661` の正規データ）。

|                             |                                    |
| --------------------------- | ---------------------------------- |
| 定義                        | 2,175 件                           |
| 名前                        | 1,470 種                           |
| `defId` が 2 つ以上ある名前 | 455 種（定義 1,160 件、53.3%）     |
| 1 つの名前の最大            | 34 通り                            |
| 重複の内訳                  | ポケモン 452 種、トレーナーズ 3 種 |
| 基本エネルギー              | 8 種すべて一意                     |

重複のほとんどはポケモンである。同じ名前でも HP もワザも進化段階も違う**別のカード**なので、
**推測で 1 つ選んではならない。** 選ぶと、例外も出ないまま別のデッキで対戦が始まる。

- 解決できない行は、**行番号と理由をつけて全部返す。** 1 件目で打ち切らない。
- 同じ名前が複数あるときは、候補を返して拒否する。候補には HP・進化段階・収録を添える。
  人はそれを見て 1 つ選び、行のうしろに `defId` を書き足す。
- 名前と `defId` の両方が書かれていて食い違うときは、どちらが本意か分からないので拒否する。
- **読み飛ばす語を持たない。** 見出しの行はカード名として解決できず `unknown-name` になる。
  カードの語彙をこのリポジトリへ書き込まないための選択である（`README.md`）。

解決は提出の時点で 1 度だけ行い、**そこから先は解決済みの `defId` 列だけを正本とする。**
対局ログに残るのもこの列で、並びも正本である（§6.2）。個体番号がデッキ配列の添字
（`p{プレイヤー}-{添字}`）である以上、同じ 60 枚でも並びが違えば別の対戦になる。

短い文字列から巨大な配列を作れないよう、行数と 1 行の枚数に上限を置く。

## 6. 対局ログ

### 6.1 正本は seed と move 列である 【決定】

1 対戦につき 1 レコード。局面もイベントも保存しない（S-4）。

実測（一様ランダムの自己対戦 20 局、`cardpool` の構成）。

| 保存する形                                | 1 局あたり |
| ----------------------------------------- | ---------- |
| seed ＋デッキ 2 つ＋ move 列（生の JSON） | 12.2 KB    |
| 同（gzip）                                | 0.63 KB    |
| 参考: 全イベントを保存した場合の生の JSON | 115 KB     |
| 参考: 1 局面の `GameState` の JSON        | 9.1 KB     |

イベントを保存すると 9 倍、局面列を保存すると 3 桁膨らむ。いずれも再生で作り直せる値である。

### 6.2 レコードの形 【決定】

```jsonc
{
  "schemaVersion": 2,
  "matchId": "...",
  "engine": {
    "commit": "...", // 起動時に env か git から。無ければ "unknown"
    "cardDataSha256": "...", // data/cards.generated.json のハッシュ
    "replaySchemaVersion": 2,
  },
  "seed": 1234,
  "seedNonce": "...", // §6.4 の公開検証用
  "firstPlayer": 0,
  "decks": [{ "cards": ["..."] }, { "cards": ["..."] }],
  "seats": [
    { "playerId": "...", "displayName": "..." },
    { "playerId": "...", "displayName": "..." },
  ],
  "startedAt": "2026-09-21T07:00:00.000Z",
  "endedAt": "2026-09-21T07:23:11.000Z",
  "moves": [
    {
      "move": { "type": "PlayBasic", "player": 0, "...": "..." },
      "elapsedMs": 4210,
      "source": "human",
      "candidates": 7, // そのときの legalMoves の数
      "chosen": 3, // その中での位置
      "offered": null, // 画面が見せた位置。全部見せたなら null
    },
  ],
  "outcome": { "winner": 0, "reason": "prizes-taken" },
  "matchResult": { "kind": "normal", "winner": 0 },
}
```

**`elapsedMs` を 1 手ごとに持つ。** 【決定】
人がその手に掛けた時間は「この局面は難しい」という無料のラベルであり、
自己対戦では絶対に手に入らない量である。エンジンは時刻を触らない（S-5）ので、
この値を持てるのはログだけである。

**`source` を 1 手ごとに持つ。** 【決定】
値は `human` のみを想定するが、欄を先に置く。将来ここに `bot` が混ざったとき、
欄が無ければ人間の手と見分けられないログが積み上がったあとで気付くことになる。

**`candidates` と `chosen` を 1 手ごとに持つ。** 【決定】
どちらも再生で作り直せる値なので、学習のために持つのではない。**持つ理由は照合である。**
エンジンを直すと合法手の集合が変わりうるが、記録した手が新しい集合にも入っていれば、
§6.4 の検査 1 は黙って通る。同じ手順で別のゲームを再生していても気付けない。
数と位置を突き合わせれば、影響を受けた対戦を機械が挙げられる。

**`offered` を 1 手ごとに持つ。** 【決定】
`legalMoves` は規則が許す手を全部返すが、画面が全部見せるとは限らない（畳む、隠す、
上位だけ見せる）。そのとき人は `legalMoves` とは別の集合の上で選んでいる。
**これは再生で作り直せない唯一の値である。** 記録しないまま学習へ渡すと、
「人がこの手を選ばなかった」という事実を、見せてもらえなかっただけの手についても学ぶ。
値はクライアントの自己申告で、手を受理するかどうかの判断には一切入らない。
全部見せたなら `null` に畳む。参照クライアント（`public/`）は合法手を全部ボタンにするので常に `null` である。

**`firstPlayer` は導出値であって、再生の入力ではない。** 【決定】
`createGame` は `config.firstPlayer` が未指定のときだけコイントスを 1 回引く。
この 1 回が乱数列を進めるので、**コイントスが出したのと同じ先攻を明示で渡しても、
そこから先のシャッフルが全部ずれる。** サーバは `firstPlayer` を渡さない。
ログの `firstPlayer` はイベント `game-started` から読んだ結果で、再生はこれを突き合わせて確かめる。
先攻をロビーや人の選択で決める仕組みを足すなら、「どちらの道で決めたか」を
レコードへ足し、再生も同じ道を通すこと。

**`outcome` と `matchResult` を分けて持つ。** 【決定】
`outcome` はエンジンの `GameOutcome` そのもの（投了と時間切れでは `null`）、
`matchResult.kind` は `normal` / `concede` / `timeout` のいずれかである（§2.3）。
学習が使えるのは `moves` を最後まで再生できる対戦だけで、その判定はこの 2 つの組で決まる。

### 6.3 エンジンの同一性 【決定】

`cardDataSha256` の不一致は**再生を拒否する**。カードの定義が変われば同じ `defId` が別のカードを指しうる。
`commit` の不一致は**警告にとどめる**。エンジンの修理は挙動を変えるが、変えるのは踏んだ対戦だけであり、
踏んだかどうかは再生すれば必ず分かる（非合法手として止まるか、`outcome` が食い違う）。
版を理由に一律で捨てると、直した誤りに触れていない大多数の対戦まで失う。

### 6.4 再生と検証 【決定】

ログ 1 行から `createGame` をやり直し、`moves` を順に `applyMove` へ通す再生器を持つ。
再生器は 4 つを確かめる。

1. すべての手が、その時点の `legalMoves` に含まれる。
2. 再生の終端の `outcome` がログの `outcome` と一致する。
3. 自己対戦が掛けている不変条件（`src/testing/invariants.ts`）が全局面で成り立つ。
4. 先攻と、各手の `candidates` / `chosen` が記録と一致する（§6.2）。

4 が要るのは、1 だけでは足りないからである。手が新しい合法手にも入っていれば 1 は通るが、
集合そのものが変わっていれば、同じ手順で別のゲームを再生したということである。
`schemaVersion` が 1 のログはこれらの欄を持たないので、この検査を掛けない。

**この再生は、ログの健全性の検査であると同時にエンジンの検査である。**
人間の対局は一様ランダムの自己対戦が踏まない筋を踏む。
`docs/roadmap-engine-completion.md` が「未知の誤りを測る手立て」として並べているものに、
実際の対戦という標本が 1 つ加わる。

シャッフルの公正さは、コミットと公開で示す。サーバは 256 ビットの乱数 `seedNonce` を引き、
`seed` をその SHA-256 の先頭 4 バイトから導く。対戦の開始時に `sha256(seedNonce)` を両者へ渡し、
終了時に `seedNonce` を公開する。**32 ビットの `seed` を直接コミットしても総当たりで開くので、この段が要る。**

### 6.5 保存先 【決定】

日付で切った JSONL（`data/matches/<日付>.jsonl`）へ追記する。データベースを置かない。
1 局 0.63 KB（gzip）なので、100 万局で 630 MB である。
学習は先頭から順に読むだけである。

**索引は置かない。** 読み返し（§6.6）だけは 1 局を名指しで引くので、走査が要る。
目当ての識別子を含まない行は解析しないふるいを通し、新しい日から見る。
実測（6,000 局・166 MB）で、最近の対戦が 32 ミリ秒、いちばん古い対戦が 847 ミリ秒である。
**一覧はこのふるいが効きにくく、6,000 局で 891 ミリ秒かかる。** 1 万局を大きく超えるなら、
走査のままでは足りない。そのときは索引を置くかどうかを決め直す。

### 6.6 読み返し 【決定】

**読めるのは自分が指した対戦だけである。** 他人が指した対戦は、存在しない対戦と同じ「無い」を返す。
デッキと引きが誰にでも見えるなら、対戦環境として成り立たない。

終わった対戦は、**当人どうしには両座席ぶんを見せる。** 相手の手札も山札の枚数も出す。
終わっている以上そこに隠す利益はなく、負けた理由を読み返せることのほうが要る。
それでも §1 の S-2 は動かない。外へ出るのは `playerView` と `projectEvents` を通った値だけで、
山札とサイドの**並び**は終わった対戦でも誰にも渡さない。

1 手ぶんの局面は、`createGame` から `ply` 手まで `applyMove` を掛けて作る。
1 局まるごと辿り直しても 50〜65 ミリ秒である（§6.1）。手数は整数に丸める。
丸めずに返すと、盤面は 2 手目の後なのに応答には 1.5 と書いてあることになる。

**開いている対戦の 1 行だけは、数局ぶん覚えておく。** 読み返しは 1 手ごとに 1 局を引き直すので、
そのたびに走査し直すと、その間ずっと進行中の対戦の手も持ち時間の見回りも止まる。
追記しかしないログなので、終わった対戦の 1 行が書き変わることはなく、覚えた値は古くならない。
索引ではない。貯めるのは開いている数局だけで、一覧（§6.5）は走査のままである。
覚えていても**座席の検査は毎回通す。**

読み返しにも §6.3 の同一性の規律を通す。`cardDataSha256` が違う記録は**読み返しを断る**。
同じ `defId` が別のカードを指しうるので、そのまま再生すると誤りを出さずに違う盤面を見せる。
`commit` の違いは**断りを付けて読ませる**。版を理由に一律で捨てると、直した誤りに触れていない
大多数の対戦まで読めなくなる。

局面には、**その手を指す直前の盤面も添える。**
手の見出しは出したカードの名前で読むが、指したあとの手札にそのカードはもう無い。
画面が 1 手戻った局面を取り直すと往復が倍になるので、サーバが一緒に返す。
添えるのも射影を通った値である。

## 7. 相手を見つける

### 7.1 待ち合わせ 【決定】

2 つだけ持つ。

- 合言葉。同じ文字列を入れた 2 人を繋ぐ。
- 待ち行列 1 本。先に待っていた 2 人を繋ぐ。

**同じ打ち手は 1 つしか待たせない。** 新しく入ってきたら、その打ち手が待っているものを先に降ろす。
別の窓を開いたり待っている間に読み込み直すと、同じ打ち手が両側に座り、
自分と自分の対戦が 1 局として記録に残って、その打ち手に 1 勝 1 敗が付く。

降りた札は、**待っている札と区別して答える。** 同じ応答にすると、降ろされた側の窓は
「相手を待っています」のまま永久に問い合わせ続ける。取りに来た札の行方は
「席が取れた」「まだ待っている」「もう降りている」の 3 つである。

**持ち点で帯を分けない。** 人が少ないうちは待ち時間が伸びるだけである。

### 7.2 打ち手と持ち点 【決定】

**持つ理由は対戦の体験ではなく、記録である。** 人の手を真似て学ぶとき、打った人の強さは
最も効く共変量になる。そして**座席と人をあとから結び直すことはできない**ので、
対戦の時点で持っていなければ、その対戦には二度と付けられない。だから、ログを貯め始める前に入れる。

**人を特定できる値を持たない。** 置くのは 3 つだけである。

| 置くもの               | なぜ                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| サーバが発行した識別子 | 対戦をまたいで「同じ人か」を言うため。対局ログに残るのはこれである |
| 本人が名乗った表示名   | 画面に出すため。本人確認ではないので、長さと制御文字だけ見る       |
| 持ち点と戦績           | 「どのくらい強いか」を言うため                                     |

メールアドレスもパスワードも置かない。学習に要るのは「同じ人か」と「どのくらい強いか」の
2 つだけで、それ以上は集めない。**公開リポジトリで動かす以上、置かずに済むものは置かない。**

認証は合言葉 1 本である。作ったときに 1 度だけ返し、**サーバは控えを持たない**
（照合はハッシュで行う）。失うとその戦績には戻れない。
**公開の識別子と合言葉は別の値にする。** 同じ値にすると、対局ログが合言葉の一覧になる。

持ち点は Elo で、初期値 1500、係数 24 とする。投了と時間切れも普通の勝敗として数える。
規則上の敗北条件ではない（§2.3）ことは対局ログの `matchResult` が区別して持っているので、
持ち点の側で分ける必要はない。**持ち点は勝敗の履歴であって、学習の終端報酬ではない。**

対局ログの `seats` に残すのは、**対戦を始めた時点の持ち点**である（§6.2）。
終わったあとの持ち点は対戦の並びから導けるので持たない。

置き場は対局ログと同じ考え方で、データベースを置かない。索引が要る問い合わせが無いためである。
書き換えは別名で書いてから差し替えるので、途中で落ちても読める版が残る。

## 8. エンジンの取り込み方 【決定】

エンジンは git submodule（`engine/`）として取り込む。npm の依存にはしない。

npm の依存にするには、エンジン側に手を入れる必要がある。エンジンの `package.json` は
`main` が TypeScript の `src/index.ts` を指し、`exports` も `types` も持たず、
`prepare` はビルドではなく git hook の設定である。ビルド（`tsconfig.build.json`）は
型定義を出さず、対象も `src` と `harness` だけである。

決め手は**カードの正規データの読み方**である。エンジンは
`data/cards.generated.json`（2.1 MB）を実行時に読み、その置き場を
「自分自身の位置から `package.json` が見つかるまで親をたどる」ことで決める
（`engine/src/cardpool/generated-cards.ts`）。submodule なら `engine/package.json` が
そのまま目印になり、この探索が何も変えずに当たる。

**submodule が指す commit は、そのまま対局ログへ刻む `engine.commit` である**（6.3 節）。
再生に使うエンジンの同一性と、依存の pin が同じ 1 つの値になる。

npm パッケージへ移すのは、エンジン側が `exports` と型定義と公開の経路を持ったときとする。
そのときサーバ側で直すのは `src/engine.ts` 1 ファイルである。

## 9. 既知の穴: `seed` が 32 ビットしかない 【未解決】

**対戦中の人は、自分の初手だけから `seed` を総当たりで割り出せる。** 割れると自分の山札の並びと
サイドの中身が全部読め、相手のデッキリストが分かっていれば相手の山札の並びも読める。
§4 の射影はこれを防がない。漏れているのは隠したカードの中身ではなく、シャッフルの入力だからである。

このリポジトリで実測して確かめたこと。

| 確かめたこと                                                           | 実測                                                                             |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 自分の手札に出る個体番号は、デッキ配列の添字そのものである             | `playerView` の `self.hand` が `p0-51` のような値を返す                          |
| その添字は相手のデッキに依存しない。攻撃側は自分の情報だけで計算できる | 相手のデッキの並びを逆にしても、自分の初手 7 枚の添字は 3 つの seed すべてで同一 |
| 初手 7 枚の添字は `seed` をほぼ一意に決める                            | 先頭 2,000,000 seed の走査で一致は 1 件                                          |
| 総当たりの速さ（`createGame` をそのまま回す、1 コア）                  | 27,400 seed/s。2^32 全域で約 44 時間                                             |

44 時間は「`createGame` を丸ごと回した場合」の上限である。シャッフルだけを書き直せば桁が変わり、
複数コアや C での実装ならさらに縮む。1 局が数十分続く対人環境では、現実的な脅威として扱うべきである。

`GameConfig` はシャッフル済みのデッキを受け取る口を持たない（`seed` と `decks` と `firstPlayer` だけ）。
`RngState` は uint32 で、`createRng` は `seed >>> 0` である。**したがってサーバ側で強い乱数を使っても
32 ビットに切り詰められる。**

取りうる道は 2 つある。

1. **エンジン側を直す。** `RngState` を広げるか、シャッフル済みのデッキを外から渡す口を足す。
   本筋だが、このリポジトリからは踏めない（エンジンは変更しない方針）。
2. **サーバ側だけで塞ぐ。** 座席へ出す個体番号を対戦ごとの不透明な別名へ置き換え、
   さらにデッキ配列を強い乱数でサーバが並べ替えてからエンジンへ渡す。**両方が要る。**
   別名だけでは、攻撃側は自分が提出した並びを知っているので添字を当てられる。
   並べ替えだけでは、個体番号がそのまま添字を教えてしまう。
   ログには並べ替えたあとのデッキを残せばよく、別名は再生に要らない。

どちらを採るかは未決定である。

## 10. 未決定事項

- **観戦の射影。** 両座席の非公開ゾーンを落とした第 3 の `view` が要る。`playerView` は viewer を
  片方の座席に取るので、そのままでは作れない。対戦後のリプレイ観戦（全公開）から先に作る。
- **打ち手の置き場の書き方。** いまは 1 つ変わるたびに `accounts.json` を丸ごと書き直す。
  `/api/account` は誰でも呼べて、回数の制限も無い。**打ち手が増えるほど 1 回の書き込みが長くなり、
  その間サーバが止まる。** 作れる速さに制限を掛けるか、書く回数を減らすか（まとめて書く、
  追記の形にする）を決める。どちらも打ち手の作り方そのものに関わるので、ここで決めてから直す。
- **複数プロセスへの分散。** 対戦は 1 プロセスのメモリに載る（1 局面 9 KB、1 手 0.2 ミリ秒の実測）。
  分散が要る規模に達していない。達したときに、対戦を座席トークンで固定の 1 プロセスへ寄せるか、
  局面を外へ出すかを決める。
- **人間の対局から学習へ渡す形。** 観測と行動の表現そのものは
  `docs/design/ai-training-loop-skeleton.md` 7 節の未決定に属する。この文書は
  「再生できる move 列を残す」ところまでを引き受ける。
